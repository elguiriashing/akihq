# AkiHQ.app OAuth return URL: migration blocker

## Reproduced configuration mismatch (2026-10-15)

The AkiHQ static application (`assets/app-v32.js`, Google login flow near line 7659) calls Supabase `signInWithOAuth` with `redirectTo: window.location.origin`. On `https://akihq.app` the required Supabase allowlisted URL is **`https://akihq.app`** (or an appropriately precise corresponding trailing-slash URL as generated by the client). Current observed result is a return to the Supabase Site URL, `https://akipasa.com/es`, with an OAuth implicit-flow token hash. This is consistent with a missing `https://akihq.app` allowed redirect; verify the hosted Supabase Auth configuration instead of assuming.

Supabase project: `vhpbvcfkcteswlsdjrfl`
URL Configuration: https://supabase.com/dashboard/project/vhpbvcfkcteswlsdjrfl/auth/url-configuration

## Required change in hosted Supabase dashboard

1. Read the existing **Site URL** and **Additional Redirect URLs**. Do not remove or replace existing entries.
2. Keep **Site URL** at its existing AkiPasa value.
3. Append exactly `https://akihq.app` and, if needed by normalization, `https://akihq.app/` to **Additional Redirect URLs**. Avoid global wildcards.
4. Verify the live Google OAuth response returns to `https://akihq.app` (not the Supabase Site URL) and that the AkiHQ SPA loads the session.
5. Test logout and subsequent login, on desktop and mobile, without posting auth URLs containing credentials.

## Source findings and caveats

- `config.js` on main still has `CRM_URL: https://crm.akipasa.com`; PR #30 changes that to `https://akihq.app` but does **not** alter the Google OAuth redirect target.
- AkiHQ SPA processes the response via Supabase JS `getSession()` during `finishBoot`; it does not use the Next.js AkiPasa `/en/auth/callback` or `/es/auth/callback` route. Do not allowlist these for AkiHQ unless the SPA is explicitly refactored to use them.
- Google provider callback at Supabase is normally `https://vhpbvcfkcteswlsdjrfl.supabase.co/auth/v1/callback`; changing a client application's web origin does not normally require modifying the Google provider callback.
- Do not implement automatic forwarding of token-bearing URL fragments to another host, or log tokens.
- A credential-bearing authentication URL was exposed during testing. Owner should revoke affected Supabase sessions and Google tokens and reauthenticate after resolution.
- An application source code fix alone will NOT fix a hosted Supabase allowlist mismatch; this requires Supabase Auth configuration.
